# Mocked / Placeholder Integrations

Nothing here is wired to a real vendor yet. Every mock lives behind a small interface so swapping in the real API is a one-file change. This document is the checklist for productionising.

> **MongoDB read-after-write consistency** (not a mock — real hardening): the app pins the correctness-critical auth/payment/upload read-after-write reads to the **primary** replica (`PRIMARY_READ` in `src/lib/db.ts`) with a `w:"majority"` write concern, so it stays correct even if the production connection string points non-critical reads at multi-region **secondary** replicas. Recommended URI: `…?retryWrites=true&w=majority`. Full detail: **docs/MONGO_CONSISTENCY.md**.

## 3. Admin authentication — SELF-HOSTED per-admin accounts (Option A implemented; managed IdP still open)

- **Where**: `apps/web/src/lib/auth.ts` (sessions/guards) + `src/lib/admin-auth.ts` (accounts) + `src/lib/admin-audit.ts` (access log) + `/admin/login`.
- **What now**: per-admin accounts in the **`admins`** collection (`{email, passwordHash (scrypt — same params as members, reused from `member-auth.ts`), role, name?, createdAt, disabledAt?}`) with three **roles** — `owner` (full), `ops` (members/support/eligibility/waitlist, NOT sign-off), `clinician` (result review + sign-off). The session cookie is still HMAC-signed but now carries the acting admin's identity: `{adminId, role, iat}` (legacy `{role:"admin"}` cookies are read as `owner` for continuity). `requireAdmin()` gates any role; `requireAdminRole(...roles)` 403s a disallowed role — the **clinician sign-off route** (`POST /api/v1/admin/results/[id]/review`, which writes the clinician note onto a member's Art.9 record) requires `clinician|owner`.
- **Bootstrap OWNER (backward compat)**: `ADMIN_PASSWORD` (+ optional `ADMIN_EMAIL`, default `owner@arcaevo.local`) is retained ONLY as a bootstrap owner credential. Login accepts EITHER `{email, password}` (per-admin account: scrypt verify, disabled check) OR password-only `{password}` (timing-safe compare against `ADMIN_PASSWORD` → OWNER session). Password-only still authenticates, so the existing e2e login (submits a password, no email) is unchanged.
- **First-boot admin auto-seed (`ensureBootstrapAdmin()`, `src/lib/admin-auth.ts`)**: the seed script (`npm run seed`) WIPES data, so it is never run in production — which would leave the `admins` collection empty and no one able to sign in to `/admin`, with no way to create the first admin (chicken-and-egg). On boot (wired into `src/instrumentation.ts` `register()`, node-runtime only, fire-and-forget, errors swallowed), when the collection is **genuinely empty** AND both `ADMIN_EMAIL` and `ADMIN_PASSWORD` are set, it creates exactly ONE real owner: `{_id: adm_<email>, email (lowercased), passwordHash: scrypt(ADMIN_PASSWORD), role:"owner", name:"Owner", createdAt, disabledAt:null}`. **Idempotent + concurrency-safe**: no-op once any admin exists (never edits/overwrites an existing account) or when the env is unset; a racing cold-start's insert hits the deterministic `_id` / unique `admins_email` index and its duplicate-key error is swallowed as a no-op. The password is never logged (only a `bootstrap owner admin created for <email>` line on creation). This **complements** the password-only break-glass: it guarantees a REAL owner DB account exists so the admin-management UI, roles and **mandatory MFA** all work — the auto-seeded owner is put through the normal first-login MFA enrolment. Intended prod value: **`ADMIN_EMAIL=accounts@arcaevo.com`**; `ADMIN_PASSWORD` is its INITIAL password — rotate after first login + MFA enrolment.
- **Access log (DPIA R4)**: **`admin_access_log`** collection + `logAdminAccess()` (fire-and-forget, never breaks a request; stores NO health values). Records every admin **login** (success + failure, with email + ip) and every admin read/write of member Art.9 data — the review-queue read (`GET /api/v1/admin/results`), member list/detail reads (`GET /api/v1/members`, `/members/[id]`), and the sign-off — as `{adminId, email, role, action, targetMemberId?, ip, outcome, at}`. Admin-management actions are logged too (`admin.account.create|disable|enable|role`, `admin.accounts.read`, `admin.access_log.read`).
- **Owner-only management UI (NEW)**: an OWNER can now manage admins and read the access log from the panel — **no direct Mongo edits**.
  - **Pages** (in the `(panel)` route group, gated by the live DB role via `currentAdmin`; shown in the sidebar to owners only): `/admin/admins` (accounts table + add-admin form + enable/disable + role-change) and `/admin/access-log` (who/what/when/target/outcome/ip, newest first, cap 200).
  - **Routes** (all `requireAdminRole("owner")` → 403 for ops/clinician, zod-validated, `admin_access_log`-written, **never** return `passwordHash` — responses go through `publicAdmin()`): `GET|POST /api/v1/admin/admins` (list / create — create lowercases email, 409 on duplicate, scrypt via `createAdmin`); `POST /api/v1/admin/admins/[id]/disable|enable`; `POST /api/v1/admin/admins/[id]/role`; `GET /api/v1/admin/access-log`.
  - **Lockout guards** (server-authoritative; the buttons mirror them as disabled + tooltip): an owner cannot **disable themselves** (`self_disable`), and the **last enabled owner** cannot be disabled or demoted out of `owner` (`last_owner`, via `countEnabledOwners()`).
- **Two-factor auth (TOTP) — IMPLEMENTED, MANDATORY for every real per-admin account** (opt-in only for the break-glass bootstrap owner): `src/lib/admin-mfa.ts` (node:crypto only, no dep). An admin can still manage their OWN 2FA from **`/admin/security`**, but a real account that has *no* MFA is forced through enrolment at login before any session is issued (see "Mandatory-MFA enrolment gate" below). RFC 6238 TOTP: HMAC-SHA1 over the 30s step, 6 digits, ±1-step tolerance; the 160-bit secret is exchanged as base32 + an `otpauth://` URI (shown as copyable text — no QR-image dep). The secret is **sealed at rest with AES-256-GCM** under a key derived from **`MFA_ENC_KEY`** (fail-closed in production, dev derives from `SESSION_SECRET`) — a DB dump alone yields no working secret; only `{ciphertext,iv,tag}` is stored. **8 single-use backup codes** are shown ONCE at enrolment (only their SHA-256 hashes are stored; verifying one consumes it). `publicAdmin()` exposes only **`mfaEnabled: boolean`** — never the secret or backup hashes.
  - **Enrolment routes** (each `requireAdmin`, act only on the caller's own account, `admin_access_log`-written): `POST /api/v1/admin/mfa/setup` (fresh secret + otpauth URI; not yet enabled) → `POST /api/v1/admin/mfa/enable` (verify a TOTP against the pending secret, then seal+persist, return the 8 backup codes once) → `POST /api/v1/admin/mfa/disable` (requires a current TOTP/backup code; owners may override — a founder policy call).
  - **Two-step login**: `POST /api/v1/admin/login` verifies the password and, if the resolved admin has MFA on, sets a short-lived (≤5 min) **signed `mfa-pending` cookie** (`{adminId, exp}` HMAC'd with `SESSION_SECRET` — carries NO role, so `readAdminSession()` rejects it and it can never stand in for a session) and returns a non-revealing `{ mfaRequired: true }` — **no session is issued**. `POST /api/v1/admin/login/mfa` (IP rate-limited) then verifies the second factor and only then mints the admin session.
  - **Mandatory-MFA enrolment gate (fixes audit A-1's MFA-bypass)**: when the **email+password** login succeeds for a real account that has **no MFA yet**, the login route does NOT issue a session — it sets a scoped **signed `mfa-enroll` cookie** (`{adminId, exp, purpose:"mfa_enroll"}`, ≤15 min, HMAC'd with `SESSION_SECRET`, **no role** — not a session) and returns `{ enrollMfaRequired: true }`. The `(panel)` layout treats "signed-in-but-not-enrolled" as **unauthorised for every data route** (`currentAdmin()` never reads the enrol cookie) and redirects to **`/admin/enroll-mfa`** (outside the panel gate, like `/admin/login`). That page drives the enrol-cookie-authorised routes **`POST /api/v1/admin/mfa/enroll/setup`** (fresh secret + URI) → **`POST /api/v1/admin/mfa/enroll/complete`** (verify a TOTP, seal+persist the secret + backup codes, **then** issue the real admin session and clear the enrol cookie). So no admin can operate without MFA. The **bootstrap password-only** path is MFA-exempt by design (break-glass): it still issues a session directly when it resolves to the synthetic `bootstrap-owner` (no DB row) — this is what keeps dev/first-login and the **e2e password login unchanged** — and is instead gated wholesale by `ADMIN_BOOTSTRAP_DISABLED` (below). When the bootstrap password binds to a real owner *with* MFA, that owner is still challenged for a second factor.
- **Rate limiting**: admin login (both steps) is IP rate-limited (`ADMIN_LOGIN_RATE_LIMIT`, ~10/5 min → 429) via the existing `rate-limit.ts` (`admin-login` + `admin-login-mfa` scopes).
- **Seed**: `npm run seed` creates a bootstrap owner (`ADMIN_EMAIL`/`ADMIN_PASSWORD` or defaults) plus a demo `ops` and `clinician` admin so the role gates are exercisable. `admin_access_log` is intentionally not wiped by re-seeds.
- **Obscured admin URL (defense-in-depth, NOT a substitute for the guards)**: the human dashboard is served under a configurable secret path segment **`ADMIN_PATH_SLUG`** (helpers in `src/lib/admin-path.ts`; `src/proxy.ts` — Next 16's renamed `middleware`, Node runtime). Requests to `/{slug}` and `/{slug}/*` are internally **rewritten** to the canonical `/admin/*` App Router tree; direct `/admin` + `/admin/*` requests **return 404 in production** so scanners probing `/admin`, `/wp-admin`, … find nothing. The slug **defaults to `admin`** (proxy is a pass-through no-op) so dev + e2e reach `/admin` with zero config; **production MUST set a long random slug**. `/admin` still works in **dev** even with a custom slug (devs aren't locked out). Every redirect target, `<Link>`/`<a>` href and `router.push` is built via `adminPath()`/`adminBasePath()` (the resolved base path is passed from server components to client components as a prop — the slug is **never** a `NEXT_PUBLIC_` var, so it never ships to the public bundle). `robots.ts`/`sitemap` still disallow `/admin` and do **not** mention the slug. The **API under `/api/v1/admin/*` is NOT obscured** (the proxy matcher excludes `/api`) — it stays guarded by `requireAdmin`/`requireAdminRole`.
- **New env vars**: `ADMIN_EMAIL` (bootstrap owner email; ALSO the identity the first-boot auto-seed keys the initial owner to — set it (e.g. `accounts@arcaevo.com`) in prod so the empty-collection auto-seed runs). `MFA_ENC_KEY` (the AES-256-GCM key material for TOTP secrets — **fail-closed in production once MFA is in use**, dev derives from `SESSION_SECRET`; now effectively required in prod since MFA is mandatory). **`ADMIN_PATH_SLUG`** (optional; secret dashboard path, default `admin` — set a long random value in prod). **`ADMIN_BOOTSTRAP_DISABLED`** (optional; `=true` rejects the shared-password bootstrap owner login entirely and drops the `ADMIN_PASSWORD` boot requirement — set it in prod once a real MFA-enrolled owner exists, security audit A-1). `ADMIN_PASSWORD`/`SESSION_SECRET` unchanged (fail-closed; `ADMIN_PASSWORD` now required to boot only while the bootstrap login is enabled).
- **Fail-closed secrets**: the cookie is a self-describing HMAC token, so the signing secret must never be a committed literal. `src/lib/env.ts` `sessionSecret()` throws in production when `SESSION_SECRET` is unset (a dev fallback is used only in non-production), and `assertRequiredSecrets()` (wired via `src/instrumentation.ts` `register()`) makes a misconfigured production server fail to boot rather than run with forgeable admin auth.
- **Still open (productionise)**: MFA is now **mandatory** for real accounts (a no-MFA account is forced to enrol before it gets a session), but **recovery policy** is still a founder decision — an owner-driven reset for a locked-out admin whose authenticator AND backup codes are lost, and the owner-override on `/mfa/disable`, are policy calls (see `docs/legal/ADMIN_AUTH_OPTIONS.md`). An **env-provided TOTP secret for the break-glass bootstrap owner** (so even the shared-password path could require a second factor) was intentionally NOT built — the `ADMIN_BOOTSTRAP_DISABLED` flag + pointing `ADMIN_EMAIL` at a real MFA-enrolled owner already cover the A-1 risk. **Password reset** is still open (an owner sets a temp password today; no self-service reset/rotation yet). And — as the team/paid tiers grow — an optional migration to a managed EU IdP (WorkOS/Auth0/Cognito) per `docs/legal/ADMIN_AUTH_OPTIONS.md` Option B. Keep the local access log either way (no IdP records *which member record was opened*).

## 7. Email (receipts, kit reminders, results-ready) — MOCK OUTBOX + OPTIONAL REAL DELIVERY (SES v2 API **or** SMTP)

- **Outbox (always)**: `apps/web/src/lib/vendors/email.mock.ts` writes every send to the console + Mongo `outbox` collection — the e2e suite (`e2e/v2-helpers.ts` token fishing, `e2e/email.spec.ts`) and admin views read it, so this write happens regardless of provider.
- **Real delivery = ADDITIONAL, env-switched (`EMAIL_PROVIDER`)** — the outbox write always happens first; then, depending on the provider, the SAME rendered email is ALSO delivered. Both paths are fire-and-forget with PII-free error logging — a transport failure never breaks the API request (load-bearing invariant). Two mutually-exclusive transports:
  - **`EMAIL_PROVIDER=ses` → AWS SES v2 API (recommended for Vercel serverless).** `email.ses.ts` signs the SES v2 SendEmail call (`POST https://email.<region>.amazonaws.com/v2/email/outbound-emails`) directly with the IAM **access key id + secret** using **AWS SigV4**, implemented dep-free with `node:crypto` (canonical request → string-to-sign → HMAC signing-key chain over date/region/`ses`/`aws4_request` → `Authorization: AWS4-HMAC-SHA256 …`, with `X-Amz-Date` + a SHA-256 payload hash). No aws-sdk, no persistent SMTP socket, native HTTPS + SES retries — a better fit for short-lived serverless invocations than keeping an SMTP connection warm. The signer is validated in `src/lib/__tests__/email-ses.test.ts` against AWS's own published SigV4 test vectors (the "deriving the signing key" example + the `get-vanilla` case).
  - **`EMAIL_PROVIDER=mailhog` (or `=smtp`) → SMTP.** `email.smtp.ts` (nodemailer) authenticates with an SMTP password *derived* from the IAM secret (or MailHog's no-auth path locally). Good for the local MailHog loop and any ESP that only exposes SMTP.
- **SMTP vs SES API — which to use**: the SMTP path needs a *derived* SMTP credential and holds a connection open (awkward on serverless, where every invocation may be a cold start); the **SES v2 API** path authenticates the HTTPS call directly with the raw IAM keys the AWS console hands you and needs no long-lived connection. **Prefer the API (`EMAIL_PROVIDER=ses`) on Vercel.** Both hit the same SES-verified `arcaevo.com` sending identity and the same least-privilege `ses:SendEmail`/`SendRawEmail` IAM user.
- **SES API env vars**: `ARCAEVO_AWS_ACCESS_KEY_ID` / `ARCAEVO_AWS_SECRET_ACCESS_KEY` / `ARCAEVO_AWS_REGION` (region `eu-west-1`), falling back to the standard `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_REGION` when the SES-specific ones are unset; `EMAIL_FROM` sets the From (default `hello@arcaevo.com`). The IAM **secret is never logged** — it lives only inside the HMAC chain.
- **Auth + TLS (OPTIONAL, env-driven — Phase 22)**: the adapter now reads credentials and TLS from env, so switching to a real ESP is a config change, not a code change. All default to the MailHog no-auth/no-TLS path when unset:
  - `SMTP_USER` + `SMTP_PASS` — if **both** are set, nodemailer gets `auth: { user, pass }`; if either is unset, no auth (MailHog). Credentials are passed straight to the transport and are **never logged**.
  - `SMTP_SECURE` — `"true"` uses TLS-on-connect (465-style); any other value (default) leaves it false for MailHog / STARTTLS on 587.
  - `EMAIL_FROM` — overrides the From address (default `Arcaevo <hello@arcaevo.com>`).
  - `SMTP_HOST` / `SMTP_PORT` — default `localhost:1026`. `buildSmtpTransportConfig()` is exported and unit-tested (`src/lib/__tests__/email-smtp.test.ts`) without opening a socket.
- **MailHog**: docker-compose `mailhog` service — SMTP on host **:1026**, web UI at **http://localhost:8026** (the standard 1025/8025 pair is taken by other local projects; inside the compose network the web container uses `mailhog:1025`).
- **Prefetch-safe sign-in code (Phase 21)**: the E1 (verify) and E2 (magic-link) emails now render BOTH the button/link AND a prominent human-typeable code (`XXX-XXX`) under it, with "Or enter this code at arcaevo.com/signin". This defends against email virus-scanners (Microsoft Safe Links, Mimecast, Proofpoint) that prefetch URLs and could burn a single-use link before the human clicks — a scanner never fills in and submits a code field. See §12 for the auth-side contract.
- To productionise: either set `EMAIL_PROVIDER=ses` + the `ARCAEVO_AWS_*` keys against the `eu-west-1` SES identity (recommended — this is the AWS-native path the founder expected), or point `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`SMTP_SECURE` at an EU-friendly ESP. Either way it is purely a config change (no code edit needed). A signed **DPA** with the processor is REQUIRED before real users (health-adjacent PII crosses it): AWS SES (EU region + AWS DPA), or **Scaleway TEM** / **Postmark EU** on the SMTP path. Then decide whether the outbox write stays as an audit log.

## 12. Member authentication (v2 web) — REAL PATTERN, DEV-GRADE PIECES

- **Where**: `apps/web/src/lib/member-auth.ts` + `/api/v1/auth/*` (signup, magic-link request/verify, signin, signout, reset request/confirm).
- **Real**: opaque 256-bit session tokens stored SHA-256-hashed in the `sessions` collection (individually revocable); scrypt password hashing (node:crypto, N=16384/r=8/p=1, optional password); 30-min single-use magic links (hash-only storage, 60s resend throttle); 5-fail → 15-min cool-off; non-revealing responses.
- **Prefetch-safe code fallback (Phase 21) — REAL**: `POST /api/v1/auth/magic-link/verify` accepts EITHER `{token}` (the emailed link) OR `{email, code}` (a Slack-style human code). Both redeem the SAME single-use token — using the code invalidates the link and vice-versa. The code is 6 chars from a 32-char unambiguous alphabet (`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, grouped `XXX-XXX`), stored hash-only as `codeHash = sha256Hex(normalizeCode(code))` on the `MagicLinkToken` doc (raw code lives only in the email). Defended by: email-scoping (the short code is meaningless without the account), 30-min expiry, single-use, and a **5-attempt ceiling** (`codeAttempts`) after which the token is burned (`consumeMagicLinkByCode` → `too_many`). Codes/tokens are never logged. Immune to email virus-scanner link prefetching; the web `/verify` screen also no longer auto-POSTs the token (a "Confirm sign-in" button does), so a prefetch that follows the link but doesn't submit can't burn it. iOS `verifyMagicLinkCode(email, code)` hits the same endpoint. Link-path 401s carry `codeAvailable: true`.
- **IP rate-limiting (security — 2026-07-05, REAL)**: `POST /api/v1/auth/magic-link/verify` (and `…/magic-link` request + `…/signin`) now sit behind a dependency-free fixed-window IP limiter (`src/lib/rate-limit.ts`, keyed by the first `x-forwarded-for`/`x-real-ip` hop). Verify + signin: ~10 attempts / 5 min / IP; link request: ~15 / 5 min / IP. Over the limit → **429** with a non-revealing message + `Retry-After`. Counters live in the Mongo `rate_limits` collection with a TTL index (`expiresAt`), so the limit holds across stateless serverless invocations — NOT in-memory. This is the IP layer **on top of** the existing per-token 5-attempt code ceiling + per-email resend/cool-off (both kept). ON by default in every environment; a local prod-build stack (e2e) opts out with `RATE_LIMIT_DISABLED=true` (`src/lib/env.ts` `rateLimitingEnabled`) so scripted bursts from one host don't flake the suite. Unit-tested in `src/lib/__tests__/rate-limit.test.ts`.
- **MOCK bits**: magic-link/verify/reset emails go to the Mongo `outbox`, never sent (§7); the legacy `demo-member-token` bearer still maps to the seeded demo member (§4); no CSRF token (cookie is SameSite=Lax + all mutations are JSON POSTs); the seed's e2e password user uses a FIXED scrypt salt for determinism — never do that in production code paths.
- **To productionise**: real ESP for link delivery; the IP limiter above is dev-grade (fixed-window, single Mongo collection) — for real scale consider a purpose-built store (Upstash/Redis) or Vercel's edge rate-limiting, and tune the thresholds; passkeys + optional TOTP at +3 months, Sign in with Apple later (linked by verified email).
- **Device-scoped sessions + silent refresh (Phase 20 — golden watch login)**: sessions now carry `device: "web"|"ios"|"watch"` (default `"web"`), an optional `expiresAt` (30-day sliding TTL, `SESSION_TTL_DAYS`) and an optional human `label`. Legacy rows without these fields read as `web` and **never expire** (backward compat); `memberFromSessionToken` treats an `expiresAt < now` row as invalid.
  - `POST /api/v1/auth/watch-session` (member auth — phone cookie OR bearer/demo token): mints a NEW `device:"watch"` session for the same user — a freshly generated token with its own row, **not** a copy of the phone token, independently revocable. **Replace policy: one active watch session per user** — a prior watch session is revoked first. `201 → { watchSessionToken, expiresAt (ISO 8601), device:"watch" }`.
  - `POST /api/v1/auth/session/refresh` (Bearer any valid session token, cookie fallback): the watch's silent-refresh on 401/wake. Revalidates + **slides** `expiresAt` to now+TTL (updates `lastSeen`). `200 → { member:{id,name,email}, device, expiresAt }`; missing/revoked/expired → `401 { error:"session_invalid" }`. (Opaque long-lived-token model: the session token IS the refresh token — "refresh" = revalidate + slide.)
  - `POST /api/v1/auth/watch-session/revoke` (member auth): deletes the user's watch-device session(s) — the phone's "sign out watch" + the admin device list. `200 → { ok, revoked }`.
  - `GET /api/v1/auth/sessions` (member auth): the member's own sessions with `device/label/lastSeen/createdAt/expiresAt/current` — **`tokenHash` is never returned**. `POST /api/v1/auth/sessions/[id]/revoke` (member auth) ends one of the member's own sessions (filter scoped to `userId`). Backs the §17 web session list.
  - The watch token is a real credential (same SHA-256 hashing, never logged, prod env gating applies) and is just another bearer session token — so it flows through `memberFromRequest` → `requireConsentedMember` and authenticates every consent-guarded health endpoint automatically once the watch holds a valid, consented session. Verified: a minted watch token → `GET /api/v1/results` 200.
  - **Seed**: the demo member (Aoife, `mem_0001`) gets a seeded `watch` + `ios` session (deterministic dev tokens `seed-watch-token-aoife` / `seed-ios-token-aoife`) for device variety in the session list + admin, and to let e2e/curl exercise refresh directly. DEV-ONLY, like `demo-member-token`.
